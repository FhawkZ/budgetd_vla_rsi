# Private completion transport v2

Added a separate socketpair for owner control, inherited only by the trusted backend process. PublicAPI continues exposing the original seven methods; completion is not a policy tool. The owner reads a real Popen exit status and supervisor pending/transport/deadline state, then sends a receipt to the backend's pinned factory and CompletionGate. The gate and native lifecycle remain on the backend's main thread. Only `completion_recorded` crosses the control channel; the score stays in the evaluator-private file. A completion attempt ends the session, so no subsequent policy action can query post-score state.

Seven process-level tests passed: normal child completion/private scoring; policy-channel completion refusal; running child refusal; abnormal child exit refusal; API timeout with no score; blocking evaluation timeout with owned backend exit; and render-error refusal. Tests used synthetic trusted factories and fresh ordinary child processes, not SAPIEN or generated robot code. Existing frozen supervisor/worker/lifecycle files are unchanged. Zero model or robot calls.

Limitations: the trusted owner must bind the supplied Popen and parsed outcome to the correct skill run. This prototype does not launch that skill itself. `render_error` must come from a trusted stderr monitor, which is not yet integrated. Cleanup currently covers the exact backend PID, not a guaranteed descendant tree. There is no private factory for real SAPIEN wired here, no complete native wall/code-line budget integration and no candidate rollout authorization. Existing10-second skill CPU limit is not native240-second wall budget. These remain required before published-source physical qualification or generated code execution.
